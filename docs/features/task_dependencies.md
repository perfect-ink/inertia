# Task dependencies and critical path

## What it does
On a folder's Gantt tab (`/folders/:id?view=gantt`) tasks can be linked so one waits on another.

- **Link types**: finish to start (default), start to start, finish to finish, start to finish. A link runs from a side of the predecessor's bar to a side of the successor's bar (`linkSides` in `data/dependency.ts`).
- **Arrows**: the shared `components/Timeline.tsx` draws one arrow per link as SVG (`links` prop). Only links with both tasks in the folder are drawn as arrows; a link with one end in another product is drawn as a stub (below).
- **Drag to link**: hovering a task bar shows a dot beyond each side (`timeline-bar-link`). Dragging from one dot onto a dot of another task bar draws a dashed provisional line and, on release, creates the link with the kind given by the two sides (`kindFromSides`: end to start is finish to start, and so on; the drag's origin is the predecessor). Dropping on empty space, the same task or an existing pair does nothing; a loop or other server rejection shows the API error notice. Esc cancels. Epic rows have no handles. The editor below stays as the keyboard way to make links.
- **Dependencies editor**: under the chart (`DependencyEditor` in `view/folder_detail/DependencyEditor.tsx`). Lists each link ("A waits on B, Finish to start") with a remove button, and a form with two task pickers, a link-type picker and Add. The editor is hidden when the folder has no tasks and no links to other projects. Server errors (loop, duplicate) show under the form.
- **Critical path**: a "Highlight critical path" checkbox (on by default). `drivingPath` starts at the dated task with the latest due date and steps back to whichever predecessor's linked date (its due date, or start date for `start_to_*` links) is latest, until a task has no dated predecessor. Those bars get the `timeline-bar--critical` class (red outline). It uses dates as entered and re-schedules nothing; fewer than two tasks on the path shows nothing. There is no slack or float.
- **Links to other projects**: a task can wait on, or be waited on by, a task in another project (or folder). Under the chart's own links, an "Other products" heading lists every link with exactly one end on this chart (`splitDependencies`, `data/dependency.ts`): "Build waits on Vendor contract (Billing) · Finish to start · Vendor contract due Nov 12", with a remove button. When the two tasks' dates no longer satisfy the link the line adds "Dates break this link by N days" in red (`externalEnd`; the task on the chart is read from the chart, so a drag shows at once, the other end is as the server sent it, and a task without a due date is never flagged). To add one, type in "Find a task in another product" (two or more letters, searched across the whole Space even with a project open); the matches join both task pickers, named with their project, and stay picked if the search is cleared. One end of a new link must be a task on this chart, otherwise Add stays off and a note says so. The server honours these links when a task's dates are saved (below).
- **Stubs on the chart**: each link in that list is also drawn on the chart as a short arrow leaving or entering the bar of the task that is on it (`components/TimelineStubs.tsx`, the `stubs` prop of `Timeline`; geometry in `linkStubs` and `placeStubs`, `data/crossProjectLink.ts`). It leaves the bar's side the link comes from (a task that is waited on: "Needed by Vendor contract (Billing)") or enters the side it goes to (a task that waits: "Waits on Vendor contract (Billing)"), with the arrowhead at the bar when entering and at the far end when leaving, and the other task and its product beside it. The label is cut short (with an ellipsis) when there is no room before the chart's edge; hovering it shows the whole note (link type, the other task's due date, broken dates). A link whose dates break gets a warning icon reading "Dates break this link by N days" and red text; one on the driving path is drawn red. Several links on the same side of one bar share a stub, with the names joined; an entering and a leaving link on the same side sit slightly apart. Stubs do not follow a bar while it is dragged, are not in the PNG export, and have no hover or click.
- **Critical path across products**: `drivingPath` also takes the tasks at the far end of those links (`externalTasks`), by the dates the server sent with the link. A task in another product can drive a task on the chart (its due date, or start date for `start_to_*` links, is compared like any other predecessor's) and then appears in the path, but the path always starts at the task with the latest due date on this chart. So a chart whose last task waits on another product's task highlights that bar and draws the stub red.
- **Moves that shift other products**: after a drag, the chart reads `rescheduled` from each update's response (`PATCH /api/v1/tasks/:id`) and, for the tasks that are not on the chart, shows "Also moved in other products: Vendor contract (Billing) to Nov 10 - Nov 14" under the toolbar (`movedElsewhere`, `movedMessage`). The note clears on the next drag. A *Block* refusal across products still shows the server's message as before.
- **Dependency mode** (ignore / block / shift) is documented in [gantt_scheduling.md](gantt_scheduling.md); it reads these links, in the browser on Gantt drags and on the server when a task's dates are saved.

## API and models
- `task_dependencies` table: `workspace_id`, `predecessor_id`, `successor_id`, `kind` (integer enum), unique index on the pair.
- `TaskDependency` validates: kind is one of the four, both tasks exist in the same workspace, no self link, no duplicate pair, no loop (breadth-first walk forward from the successor). `workspace_id` defaults from the predecessor.
- `Task` destroys its links in both directions (`successor_links`, `predecessor_links`).
- `Scheduling::TaskUpdate` (used by `PATCH /api/v1/tasks/:id`) reads a task's links when its dates change and, per its folder's mode, refuses the change or moves the tasks that wait on it; see [gantt_scheduling.md](gantt_scheduling.md).
- `GET /api/v1/task_dependencies` (all of the Space's links, not filtered by folder or by the open project) returns each link with both ends as `predecessor` and `successor` (`TaskLinkBlueprint`: `id`, `title`, `status`, `start_date`, `due_date` and `folder_id`, which is the task's own folder or else its document's), so a link to another project can be named, dated and placed without loading that project's tasks. `POST` (`task_dependency[predecessor_id, successor_id, kind]`; unknown task ids in the Space give 404, validation errors give 422 with `errors`), `DELETE /:id`. There is no update; changing a link type means removing and re-adding.
- `GET /api/v1/tasks?all_projects=true` lists the whole Space even when `X-Project-Id` names a project (`TasksController#all_projects?`), which is how the editor's search reaches other projects; `useTaskSearch` in `api/tasks.ts` sends it with `q`. Changing a task refreshes the cached links, because they carry the tasks' dates.
- Frontend hooks: `api/taskDependencies.ts`, `useTaskSearch` in `api/tasks.ts`; the search is debounced by `hooks/useDebouncedValue.ts`.

## Known limits
- Drag-to-link is pointer only; keyboard users use the editor's pickers. The handles are invisible until a bar is hovered, so touch screens cannot use them.
- The critical path is "what drives the latest finish today", not a scheduled critical path: no slack, no float, and it only follows the task with the latest due date.
- Links where neither end is on the chart do not show there; open the chart of either end. The "Other products" wording (and the stub) also covers a task in another folder of the same product (its product name is shown). A stub label can be cut short at the chart's edge: the stub stays and the name is shortened (hover for the rest). The critical path passes through the other task but not on past it to that task's own predecessors, unless those links also touch this chart.
- The Dependency mode of the task that is moved decides what its links across projects do, on the server: *Block* refuses a move that would break a link to another project, and *Shift* moves the tasks that wait on it in other products too. Decision: the browser's own check (`planReschedule`) stays chart-only on purpose, because it has only this chart's tasks and not the other products' own links; the server is the authority and the chart reports what it did, from `rescheduled` in the response (see "Moves that shift other products" above). So a *Block* refusal across products arrives from the server after the drag instead of before it, and the chart sends nothing for tasks in other projects itself.
- The broken-dates note on a link to another project uses the other task's dates as of the last time the links loaded; it refreshes when any task is changed from this app, not when someone else changes it.
- The Space-wide list of links between products is on the Portfolio (see [portfolio.md](portfolio.md)).
- Creating, changing or removing a link never moves any dates, whatever the mode.
